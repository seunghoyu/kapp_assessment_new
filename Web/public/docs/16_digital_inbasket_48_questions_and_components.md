# 디지털 인바스켓: 문항 48개 vs 컴포넌트 16개

> 학습자 LMS에서 디지털 인바스켓 문항이 **16개로 보이는 이유**, 원본 digital_inbasket에서 **48개로 보이는 이유**, 그리고 **컴포넌트 개수와의 관계**를 정리한 문서입니다.

---

## 1. 요약

| 구분 | 원본 digital_inbasket | 학습자 LMS(Next.js) 현재 |
|------|------------------------|---------------------------|
| **문항 개수** | API/DB 기준 **48개** (또는 N개) | **16개** (더미 JSON: 타입당 1개) |
| **시뮬레이션 타입(카테고리)** | **16가지** 고정 | **16가지** 동일 |
| **UI 컴포넌트 개수** | **16개** (타입별 렌더 함수 1개) | **16개** (타입별 React 컴포넌트 1개) |

- **48개** = **문항(데이터) 레코드 수** 이며, **컴포넌트가 48개라는 뜻이 아닙니다.**
- 화면을 그리는 **시뮬레이션 UI는 16종**만 있습니다. 문항 48개는 이 16가지 타입에 **여러 개씩** 매핑됩니다.

---

## 2. 원본 digital_inbasket에서 48개가 이루어지는 방식

### 2.1 데이터 출처

- 원본은 **RESTful Table API** 로 문항을 가져옵니다.
  - **GET** `tables/questions?limit=100`
  - 응답: `{ data: [ { id, title, category, sender, date, priority, content, attachments }, ... ] }`
- 실제 **DB(또는 백엔드)에 저장된 문항이 48개**이면, 화면에는 **48장의 카드**가 목록으로 노출됩니다.
- README에는 “22개 이상의 실무 문항”이라고 되어 있으나, **운영/테스트 환경에서 문항을 48개까지 넣어 두었다면 48개가 표시**됩니다.

### 2.2 문항과 카테고리(타입)의 관계

- 각 문항은 **`category`** 필드로 **16가지 시뮬레이션 타입 중 하나**에 속합니다.

| category (16가지) | 직무 매핑(필터용) |
|-------------------|--------------------|
| 이메일 관리, 메신저 대응 | 커뮤니케이션 |
| 보고서 작성, 일정 관리, 전략 기획 | 경영/기획 |
| 통합 업무, 글로벌 협업 | 프로젝트관리 |
| 위기 관리 | 위기대응 |
| 인사 관리 | 인사/조직 |
| 재무 관리 | 재무/회계 |
| 디지털 활용 | IT/디지털 |
| 법무 검토, 윤리 경영 | 법무/컴플라이언스 |
| 고객 관리 | 고객서비스 |
| 마케팅캠페인 | 마케팅/영업 |
| 생산관리 | 생산/운영 |

- 따라서 **48개 문항** = 16가지 타입에 **타입당 평균 3개** 정도 분포한다고 보면 됩니다. (예: 이메일 3개, 메신저 2개, …)
- **같은 `category`를 가진 문항이 여러 개** 있을 수 있고, 문항을 클릭해 시뮬레이션에 들어가면 **그 문항의 `category`에 해당하는 UI 1종**만 사용합니다.

### 2.3 데이터와 화면의 연결

1. **목록 화면 (index.html / main.js)**  
   - `fetch('tables/questions?limit=100')` → 받은 **문항 배열 전체**를 카드로 표시.  
   - 48개면 카드 48개.
2. **직무 필터**  
   - 문항의 `category`를 위 표처럼 12개 직무로 매핑해, 직무별로 필터링·개수 표시.
3. **시뮬레이션 화면 (simulation.html / simulation.js)**  
   - URL `?id=문항ID` 로 **문항 1개** 조회: `fetch('tables/questions/' + id)`.  
   - 해당 문항의 **`category`** 값에 따라 **16개 렌더 함수 중 하나**만 호출:
     - 예: `category === '이메일 관리'` → `renderEmailManagement(question)`
     - `category === '메신저 대응'` → `renderMessengerApp(question)`  
   - 즉, **문항이 48개여도 화면을 그리는 로직은 16가지**뿐입니다.

### 2.4 컴포넌트 개수

- 원본에서 **“컴포넌트”**에 해당하는 것은 **simulation.js** 안의 **타입별 렌더 함수 16개**입니다.
  - 이메일 관리, 메신저 대응, 보고서 작성, 일정 관리, 통합 업무, 위기 관리, 글로벌 협업, 법무 검토, 디지털 활용, 인사 관리, 재무 관리, 고객 관리, 윤리 경영, 전략 기획, 마케팅캠페인, 생산관리.
- **48개 문항 ≠ 48개 컴포넌트**입니다. **16개 타입 = 16개 UI(컴포넌트)** 이고, 48개는 **그 16가지 UI를 쓰는 문항이 48개**인 것입니다.

## 3. 학습자 LMS(Next.js) 쪽 현재 구조

### 3.1 문항이 16개로 보이는 이유

- 학습자 LMS에서는 **API 대신 JSON 더미**를 사용합니다.
  - 경로: `data/kappDiagnosis/inbasket/inbasketQuestions.json`
  - 현재 **`questions` 배열에 16개**만 넣어 둔 상태입니다.
  - **16가지 시뮬레이션 타입당 1개씩** 넣어, “각 타입이 한 번씩은 보이도록” 한 구성입니다.
- 따라서 **목록에 16개**만 보이고, **48개가 아닙니다.**

### 3.2 컴포넌트 개수

- Next 앱에서도 **시뮬레이션 UI 컴포넌트는 16개**입니다.
  - `app/app/diagnosis/inbasket-simulations/` 아래:
    - EmailSimulation, MessengerSimulation, ReportSimulation, CalendarSimulation, … ProductionSimulation
  - 문항의 **`category`** 로 위 16개 중 하나를 골라 렌더링합니다.
- 문항을 48개로 늘려도 **컴포넌트는 그대로 16개**입니다. 문항만 48개 레코드로 늘리면 됩니다.

### 3.3 48개로 늘리는 방법

- **같은 스키마**로 `inbasketQuestions.json`의 `questions` 배열에 **문항을 48개** 넣으면 됩니다.
  - 예: 이메일 관리 3개, 메신저 대응 3개, … 식으로 타입별로 여러 개.
  - 각 문항은 기존처럼 `id`, `title`, `category`, `jobCategory`, `sender`, `date`, `priority`, `content`, `attachments` 를 가지면 됩니다.
- **직무 필터**는 `jobCategory`(또는 `category`→직무 매핑)로 그대로 동작합니다.
- **시뮬레이션 진입** 시 해당 문항의 `category`에 따라 위 16개 컴포넌트 중 하나가 선택됩니다.

## 4. 보충: "48개 모두 UI가 다른데 왜 컴포넌트는 16개인가?"

### 4.1 "다르다"의 두 가지 의미

48개가 **각각 다르다**고 할 때, 다음 둘을 구분해야 합니다.

| 구분 | 의미 | 개수 |
|------|------|------|
| **화면 종류(레이아웃)** | 이메일 클라이언트형, 메신저형, 캘린더형, 위기 대응형 … 처럼 **화면 틀·UI 타입**이 다른 것 | **16가지** |
| **시나리오(내용·데이터)** | 문항마다 **제목, 발신자, 본문, 상황 설명** 등이 다른 것. 즉 "풀어야 할 문제"가 48가지 | **48가지** |

- **컴포넌트 16개** = **화면 종류(레이아웃)** 가 16가지라는 뜻입니다.  
  예: "이메일 관리" 컴포넌트 1개로, **이메일 관리 타입 문항 여러 개**를 모두 같은 화면 틀(목록+본문+답장/전달 버튼)로 보여 줍니다.
- **48개 시뮬레이션이 다르다** = **시나리오(데이터)** 가 48가지라는 뜻입니다.  
  같은 "이메일 관리" UI를 쓰는 문항 3개라도, **제목·발신자·본문**이 다르면 학습자 입장에서는 "다른 시뮬레이션"으로 느껴집니다.

정리하면, **UI(화면 틀)는 16종**이고, **그 16종 안에 서로 다른 데이터(시나리오) 48개**가 들어 가는 구조입니다. 그래서 컴포넌트는 16개인데, "48개 모두 시뮬레이션이 다르다"는 말은 **데이터/시나리오가 48가지**라는 의미로 맞습니다.

---

## 5. 보충: 48개 시뮬레이션(데이터)의 구성과 연결

### 5.1 데이터 구성

- **48개 문항** = **48개의 시뮬레이션 데이터 레코드**입니다.
- 각 레코드(문항)는 대략 다음처럼 구성됩니다.

| 필드 | 설명 |
|------|------|
| **id** | 문항 고유 ID (예: `inbasket_email_1`, `inbasket_email_2` …) |
| **title** | 문항 제목 (시나리오마다 다름) |
| **category** | 이 문항이 쓰는 **화면 종류** (16가지 중 하나. 예: `"이메일 관리"`, `"메신저 대응"`) |
| **sender** | 발신자 (문항마다 다름) |
| **date** | 날짜/시간 표시 (문항마다 다름) |
| **priority** | 우선순위 (긴급/보통/낮음) |
| **content** | 본문/시나리오 설명 (문항마다 다름) |
| **attachments** | 첨부 목록 (있으면 문항마다 다름) |

- **시뮬레이션이 48개 다르다** = 위 필드들(**title, sender, content** 등)의 조합이 문항마다 다르다는 뜻입니다.  
  같은 `category`(예: 이메일 관리)를 가진 문항이 3개 있으면, **화면 레이아웃은 동일**하지만 **채워 넣는 데이터가 3벌**입니다.

### 5.2 연결 흐름 (어떻게 구성되고 어떻게 연결되는지)

1. **목록**
   - 48개 문항 배열을 한 번에 가져옴 (API: `tables/questions?limit=100` 또는 JSON 48개).
   - 각 문항의 **id, title, category, sender, date, priority** 등으로 **카드 48장**을 그림.
   - 문항을 클릭하면 **그 문항의 id**로 상세/시뮬레이션으로 넘어감.

2. **시뮬레이션 진입**
   - 선택한 문항 **id**로 **해당 문항 1건**만 조회 (API: `tables/questions/{id}` 또는 배열에서 id로 찾기).
   - 조회한 객체를 **question** 이라고 부름. 이 **question**이 곧 "그 시뮬레이션의 데이터 전체"입니다.

3. **화면 선택 (16개 중 1개)**
   - **question.category** 값을 본다 (예: `"이메일 관리"`, `"메신저 대응"`).
   - **category**에 따라 **16개 컴포넌트(또는 렌더 함수) 중 하나**를 골라, 그 컴포넌트로 화면을 그림.

4. **데이터 연결 (같은 UI, 다른 내용)**
   - 선택된 **컴포넌트**에 **question** 전체를 넘긴다 (예: `props.question` 또는 `renderEmailManagement(question)`).
   - 컴포넌트 안에서는 **question.title**, **question.content**, **question.sender**, **question.date** 등을 읽어서 화면에 채운다.
   - 따라서 **같은 "이메일 관리" UI**라도, 문항 A와 문항 B는 **서로 다른 title·content·sender** 때문에 **다른 시뮬레이션**으로 보입니다.

요약하면:

- **구성**: 48개 문항 = 48개의 **데이터 레코드** (각각 id, title, category, sender, content 등).
- **연결**:  
  **문항 id** → 해당 문항 데이터 1건 조회 → **question.category**로 **16개 UI 중 1개 선택** → 그 UI에 **question**을 넘겨서 **문항마다 다른 데이터**를 표시.  
  그래서 **데이터는 48가지로 다르고**, **화면을 그리는 컴포넌트는 16개**입니다.

## 6. 정리 (데이터 vs 컴포넌트)

| 항목 | 설명 |
|------|------|
| **48개** | 원본에서 **문항(데이터) 레코드 수**. 각 문항 = 서로 다른 시나리오(제목·발신자·본문 등). API/DB에 48개 있으면 목록에 48장 카드. |
| **16개** | **화면 종류(UI 타입)** = **컴포넌트(또는 렌더 함수) 개수**. 같은 화면 틀에 48개 문항 데이터를 넣어서 보여 줌. |
| **연결** | 문항 **id** → 해당 문항 1건 조회 → **category**로 16개 UI 중 1개 선택 → 선택된 UI에 **question** 넘겨서 문항마다 다른 내용 표시. |
| **학습자 LMS 현재** | 더미 문항 16개(타입당 1개)만 있어서 16개로 보임. 48개로 보이게 하려면 JSON에 문항 48개 추가하면 됨. |

이 문서는 학습자 LMS 문서 드롭다운(학습자 LMS ▾)에 포함됩니다.
